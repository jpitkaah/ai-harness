Answers to the open questions in "Failure patterns: Qwen 2.5 3B harness on GPQA and IFBench" (2026-10-10)

From the runs already made on 2026-10-10 (v17 = strat2.py = best_strat.py). No new test runs were made
for these answers.


1. Why does the probe with the current samples score 67 when v17's full run scored 75?

Two reasons, both visible in the data.

a) It is not the same computation. The full run lets the model write "The correct answer is (C)" one
   token at a time. The probe puts "The correct answer is (" into the prompt and reads the next token's
   probabilities. llama.cpp doesn't promise identical numbers for text read as part of a prompt (in a
   batch) and text generated token by token. Many GPQA questions are near-ties: on the hard set the right
   letter was a close second 10 times, 6 of them within 0.13 of the top letter. A tiny difference flips
   such a question. Against v17's full run, the probe kept 65 of its 75 right answers and got 2 of its 123
   wrong ones right: 67.

b) The probe also moves between identical runs. The same three sample variants scored 71, 75 and 68 in
   one run and 67, 73 and 66 in the next: up to 4 of 198. Both probe runs had the prompt cache on (see
   question 3).

So the probe is fine for relative questions, such as whether the letter bias comes from the samples (it
doesn't). It is not a stand-in for the full run's score.

3. Does cache_prompt: false remove the run-to-run noise on this backend?

It reduces the noise but doesn't remove it. Same code (v17), each control set run twice back to back:

                                             cache on    cache off
  IFBench replies identical in both runs      15/30       24/30
  IFBench prompts whose pass/fail flipped      3           1
  IFBench control score (two runs)             24, 25      23, 22
  GPQA replies identical in both runs         26/30       27/30
  GPQA control score (two runs)                27, 28      28, 28

With the cache on, results also depend on what ran just before: the same IFBench control set scored 20/30
when the hard set had run first.
- Tests now send cache_prompt false (harness.CACHE_PROMPT). The chat app keeps the cache, which is about
  30% faster on IFBench.
- What's left is about 1 flip per 30-item set, from the backend itself. It shows most on IFBench, where
  one changed token changes the rest of a long answer.

4. Have DRY or other repetition penalties already been tried and logged in FAILED_EXPERIMENTS.md?

No. Neither FAILED_EXPERIMENTS.md nor plan.md has an entry for DRY or for a repeat, frequency or
presence penalty.
- The only sampler trial: strat2 v4 (temperature 0.2 / 0.8 and min_p 0.1, 2026-10-09) scored 16/30
  against 17/30, within the noise.
- After that the user ruled out sampler changes. CLAUDE.md: "Never tune temperature or sampler settings
  (min_p, top_k, ...) to change scores." DRY is a sampler setting, so it needs the user's OK before any
  trial.

What the harness does instead is its own repetition check:
- A reply that repeats a 4-word phrase (normal route) or a 10-word phrase (long route) is cut off and
  rejected, and the next attempt gets a note (harness.run_checks).
- A reply cut this way is never accepted. It reaches the results only as the fallback: when all three
  attempts are rejected, the last one is used (marked "unchecked" in the app).
- So every truncated IFBench reply that ends on a repeated phrase is such a fallback.

Does DRY act at temperature 0? Not tested here. In llama.cpp's sampler chain the penalties and DRY come
before the temperature step, so they should still change which token is most likely. Unverified.

Update (2026-10-10, after these answers): the user allows DRY. Their one rule for the harness is not to
hard-code anything very specific that helps the code solve a certain test question. Test answers stay at
temperature 0.
